# Gemma 4 开发者智能体比赛：信息调研与参赛准备

> 调研日期：2026 年 10 月 9 日，北京时间（UTC+8）。  
> 比赛：Google - The Gemma 4 Developer Agent Competition。  
> 本文依据比赛官方页面、官方入门笔记本和工作人员公告整理。规则、运行环境及排队策略可能调整，正式参赛时应再次核对原始页面。

## 1. 比赛目标与基本信息

这场比赛要求构建能够自主解决软件问题的编码智能体（Agent）：收到问题描述和代码仓库后，定位相关代码、修改实现、验证结果，并生成可应用的代码补丁。任务涵盖真实 Python 缺陷修复和功能需求，主赛以测试通过率排名。

比赛希望推动开放模型在离线、有限算力条件下完成多轮软件工程任务。可以改进提示词、工具使用、技能、流程和模型适配；低秩适配（Low-Rank Adaptation, LoRA）是可选项，因此可以先建立无需训练的基线，再研究后训练（Post-training）。

| 项目 | 已核实的信息 |
| --- | --- |
| 主办方 | Google DeepMind；规则中的赞助方为 Google LLC |
| 主赛类型 | 精选预测比赛（Featured Prediction Competition） |
| 主赛评测目标 | 代码补丁能否通过相应验证测试 |
| 必须使用的基础模型 | `gemma-4-31b-it-qat-w4a16-ct` |
| 可选配套赛道 | 论文赛道（Paper Track），独立报名和提交 |
| 主赛奖励 | 65,000 美元；提供 Kaggle 积分和奖牌 |
| 两条赛道合计奖金 | 100,000 美元 |

来源：[主赛概览](https://www.kaggle.com/competitions/gemma-4-developer-agent)、[数据说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/data)、[奖金说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/prizes)、[完整规则](https://www.kaggle.com/competitions/gemma-4-developer-agent/rules)。

## 4. 评分方式、榜单与时间预算

### 4.1 评分单位是完整任务

评测采用通过 / 失败（PASS/FAIL）判定：将智能体补丁应用到对应仓库，再运行该任务的验证测试。分数是成功修复任务的比例，可概括为：

```text
得分 = 通过验证的任务数 / 对应评测集合的任务总数
```

它不要求补丁文字与参考答案完全一致；能否通过验证才决定结果。通过部分测试不能直接当成该任务已经得分。

来源：[主赛评测说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/evaluation)。

### 4.2 三种数据范围需要分清

| 范围 | 用途 | 参赛期间可见性 |
| --- | --- | --- |
| 公开开发集 | 开发、训练、离线验证 | 可获取任务和参考材料 |
| 公开榜测试部分 | 生成公开排行榜（Public Leaderboard）成绩 | 测试内容隐藏，成绩可见 |
| 私有榜测试部分 | 决定最终排行榜（Private Leaderboard）排名 | 测试内容与成绩在比赛期间隐藏 |

数据页称隐藏测试集约 120 题，两部分均分，即各约 60 题；这些测试任务来自私有仓库。**公开开发集的 129 题与公开榜测试题不是同一集合。** 最终名次由私有榜决定；规则规定同分时，较早提交者优先。

来源：[数据说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/data)、[规则中的胜者判定](https://www.kaggle.com/competitions/gemma-4-developer-agent/rules)。

### 4.3 12 小时覆盖全部隐藏测试任务

官方给出的补丁生成总预算是 **12 小时**，包含沙箱（Sandbox）准备时间，不包含随后补丁验证时间。可在 `eval_config.yaml` 中设置每题限制。

Kaggle 工作人员进一步澄清：**每次提交都会运行公开榜和私有榜的全部测试任务**，以便提前发现私有部分的运行错误。拿到公开榜分数表示评测流程也已在私有部分完成，不表示私有任务全部修复成功。

来源：[评测说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/evaluation)、[工作人员关于全量评测的回复](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/746008)。

**预算估算与建议，非官方默认参数：**

- 按约 120 题估算，`720 分钟 / 120 ≈ 6 分钟/题`，还需扣除环境准备开销。
- 不宜简单给每题 6 分钟的推理上限后就假定总时长必然合规；需测量实际准备时间与长尾耗时。
- 使用时间限制、工具调用上限和轮次上限共同约束成本，并预留生成、检查和提交补丁的时间。
- 尽早结束无进展的重复搜索，保住已完成修改；给更有希望通过的任务留出测试和修正机会。

## 5. 提交内容与实际流程

### 5.1 交付的是智能体配置包

正式提交文件是 **`submission.zip`**，压缩包根目录必须直接包含 **`agent.yaml`**。配置采用 Google 智能体开发套件（Agent Development Kit, ADK）的配置机制，并受比赛的安全和运行约束限制。

下面是便于理解的目录示意。除 `agent.yaml` 外，按实际方案选择其他文件，具体字段以官方样例为准。

```text
submission.zip
├── agent.yaml
├── eval_config.yaml                 # 可选：每题运行限制
├── prompts/
│   └── system.md                     # 提示词
├── configs/
│   └── sampling.yaml                 # 生成参数
├── sub_agents/
│   └── analyzer.yaml                 # 可选：子智能体
├── adapters/
│   └── repair_adapter/
│       ├── adapter_config.json
│       └── adapter_model.safetensors
└── skills/
    └── navigation/
        ├── SKILL.md
        ├── scripts/
        └── resources/
```

来源：[提交格式](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/evaluation)、[官方入门笔记本](https://www.kaggle.com/code/ryanholbrook/getting-started-gemma-4-developer-agent)。

### 5.2 官方示例展示的工作流程

1. 在比赛笔记本（Notebook）中挂载比赛数据、指定模型和官方离线依赖包。
2. 将 `sample_submission/` 复制到可写目录，再调整配置。
3. 启动本地 vLLM 推理服务，注册基础模型和可选适配器。
4. 在少量公开开发题上生成补丁，并执行验证。
5. 打包生成 `/kaggle/working/submission.zip`，检查大小和文件格式。
6. 保存并成功运行笔记本版本，确认输出文件存在，再通过比赛入口提交。

工作人员明确说明：笔记本需先生成 `submission.zip`，评分系统才能评测。官方入门示例属于流程演示，其公开输出的两个小样本均未完成修复，不能把“笔记本运行成功”理解为“方案已有可靠修复率”。

来源：[官方入门笔记本](https://www.kaggle.com/code/ryanholbrook/getting-started-gemma-4-developer-agent)、[工作人员关于提交文件的说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743683)。

### 5.3 `submission.parquet` 的角色

数据页说明，评测框架运行配置包后会生成 `submission.parquet`，保存每题结果：`id` 是任务标识，`prediction` 是统一差异格式的补丁；没有修改时可能为 `NO_PATCH`。这个运行结果文件与参赛者提交的 `submission.zip` 承担不同角色。

来源：[数据说明中的输出文件定义](https://www.kaggle.com/competitions/gemma-4-developer-agent/data)。

## 6. 模型、适配器、工具与技能限制

### 6.1 指定基础模型与可选适配器

所有主智能体和子智能体都必须使用 `gemma-4-31b-it-qat-w4a16-ct`。允许提交一个或多个参数高效微调（Parameter-Efficient Fine-Tuning, PEFT）的 LoRA 适配器，不同智能体可选择不同适配器。

每个适配器目录放在 `adapters/<名称>/`，包含 `adapter_config.json` 与 `adapter_model.safetensors`，并通过智能体配置中的 `adapter` 字段引用。

规则允许符合条件的外部数据和开发工具，但**最终评测的单基础模型限制仍然适用**。外部模型生成训练轨迹、蒸馏材料等具体方案，应在确定数据来源、许可和使用方式后核对官方要求。

来源：[模型与框架要求](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/model-selection-budget-and-harness-rules)、[外部数据条款](https://www.kaggle.com/competitions/gemma-4-developer-agent/rules)。

### 6.2 官方预定义工具

| 工具标识 | 用途 |
| --- | --- |
| `run_command` | 在 `/workspace` 内执行 Bash 命令 |
| `read_file` | 读取文件，可指定行范围 |
| `edit_file` | 替换文件中的目标文本 |
| `write_file` | 创建或覆盖文件 |
| `get_status` | 查询预算消耗与补丁状态 |
| `submit_patch` | 收集工作区相对 `HEAD` 的差异作为补丁 |
| `get_code_neighbors` | 查询代码符号的图邻居 |
| `search_similar_code` | 查询向量相似的代码节点 |
| `get_code_subgraph` | 提取指定节点之间的子图 |

自定义子智能体通过 `agent_tool` 配置。`!include` 路径相对包含该指令的文件解析，不能越出提交根目录；不能通过路径穿越或符号链接绕过沙箱。

技能（Skill）目录需有带 `name` 前置元数据的 `SKILL.md`。技能脚本由 `run_skill_script` 在沙箱内运行，其时间计入预算；知识资源可由 `load_skill_resource` 读取。自定义脚本应通过规定的技能机制运行。

来源：[官方工具与技能要求](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/model-selection-budget-and-harness-rules)。

### 6.3 提交大小与示例配置

官方入门笔记本对**解压后的文件总大小**执行 3 GiB 上限检查，并从比赛库导入允许的文件扩展名进行验证。训练后的适配器也需要计入大小；打包验证应调用当前版本的官方检查逻辑。

示例使用 `max_model_len=32768`，并读取 `timeout_seconds`、`max_tool_calls`、`max_time_minutes`、`max_turns` 等评测参数。这些是已查看示例的设置和字段，不能据此断言所有可调参数及硬限制。本次未读取受访问限制的完整 `HARNESS_README.md`。

来源：[官方入门笔记本的推理、评测与打包代码](https://www.kaggle.com/code/ryanholbrook/getting-started-gemma-4-developer-agent)。

## 7. 数据与运行环境

### 7.1 数据中最需要理解的部分

公开开发集有 129 题，来自 `fastapi/fastapi`、`Textualize/rich`、`psf/requests` 和 `encode/httpx`。数据页在调研时显示约 22.42 GB、524 个文件；文件规模可能随更新改变，模型和推理依赖另计。

| 文件 / 目录 | 主要作用 |
| --- | --- |
| `tasks.jsonl` | 每行一个任务；记录仓库、问题、基准提交和参考材料 |
| `snapshots/` | 各题修复前的 Git 仓库快照，后续历史已移除 |
| `graphs/` | 基于抽象语法树（Abstract Syntax Tree, AST）的调用与依赖图 |
| `embeddings/` | 节点的 256 维 `float32` 向量，供离线检索 |
| `wheels/` | 沙箱离线安装仓库依赖所需的预编译包 |
| `docker/`、`sandbox/` | 容器构建、兼容性处理和任务初始化 |
| `sample_submission/` | 智能体配置样例 |
| `HARNESS_README.md` | 完整评测框架（Harness）技术说明 |

`tasks.jsonl` 的主要字段是 `instance_id`、`repo`、`base_commit`、`problem_statement`、`hints_text`、`patch`、`test_patch`、`created_at`。公开材料包含参考修复 `patch` 和验证测试 `test_patch`；隐藏评测不会向智能体提供参考修复，验证测试也由评测方保存。

官方筛选流程要求：修复前验证测试失败，应用参考修复后测试通过。测试集还经过更强模型的可解性检查。

来源：[完整数据说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/data)。

### 7.2 开发材料与公平验证的使用方式

**以下是参赛建议：**

- 可用公开参考补丁分析修复模式、构造训练材料，用验证测试测量修复是否成立。
- 测量智能体能力时，应给智能体与隐藏评测相近的输入，避免直接暴露参考补丁或私有验证测试内容。
- 将训练题和验证题分开；相同 `base_commit`、相近问题或重复修复尽量放在同一分组，减少信息泄漏。
- 将任务成功率、参考补丁成功率和环境故障率分别记录。若参考补丁也无法通过，先调查环境或数据问题。
- 除随机划分外，考虑按仓库留出验证，检查方案能否迁移到未针对性优化的代码库。

### 7.3 计算资源与离线条件

比赛提供 4 张 NVIDIA L4 的运行机器，总显存 96 GB。官方规定 L4 会话必须关闭互联网，只能用于附属于本比赛的笔记本；其配额消耗目前是旧 T4×2、P100 机器的两倍，组织者可能进一步调整。

官方数据说明中的沙箱提供 Python 3.13 和离线依赖安装。入门笔记本另挂载官方依赖包仓库（Wheelhouse），用于配置推理服务和评测库；它与比赛数据中的 `wheels/` 用途不同。

来源：[计算资源说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview/upgraded-accelerators)、[数据说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/data)、[官方入门笔记本](https://www.kaggle.com/code/ryanholbrook/getting-started-gemma-4-developer-agent)。

**对当前项目的建议：** 当前 `pyproject.toml` 声明 Python `>=3.13`，可先用于本地任务分析和配置管理。推理与正式评测仍应优先在官方运行环境验证，不能仅凭本地版本号一致就假定依赖兼容。

## 9. 调研时的官方公告与实际影响

### 9.1 代码图缺少异步函数

主办方确认，代码图工具没有收录 `async def` 函数，会影响部分 FastAPI、HTTPX 公开开发题。主办方表示，来自私有仓库的测试任务不修改这类函数，因此不会更新私有任务代码图。

**开发建议：** 图检索失败时回退到文件、符号和文本搜索；不要因为图里没有某符号就判定源码不存在。验证时可单独记录受图覆盖问题影响的题目。

来源：[主办方代码图公告](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/745998)。

### 9.2 排队、平台错误与待评分提交限制

2026 年 10 月 9 日查阅的工作人员公告称：部分提交因排队超过 15 小时被标成平台错误（Kaggle Error）；平台已延长排队容许时间，并重新处理受影响的有效提交，无需参赛者重交恢复。

公告还说明正在实施独立的待评分提交限制：队伍上一份提交仍在评分时，需要等待其完成后再次提交。此限制与每天 1 次的限制并存。

**开发建议：** 区分平台排队错误、配置错误、推理失败和补丁验证失败；不要把所有无分数情况都归为模型质量问题。提交前查阅该公告最新进展。

来源：[工作人员排队与错误更新](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/747519)。

## 10. 可选论文赛道

论文赛道要求原创、未发表研究，最长 **3,000 词**。以 Kaggle 研究报告（Writeup）提交，包含标题、摘要、引言、方法与实验、相关工作和引用；可选附公开笔记本或通过公开项目链接提供论文 PDF。提交不阻止后续投往其他会议或渠道。

| 评审维度 | 中文理解 |
| --- | --- |
| 新颖性（Novelty） | 新发现或新见解 |
| 质量（Quality） | 方法的普适性与泛化 |
| 相关性（Relevance） | 对软件工程与智能体学习的意义 |
| 可验证性（Verifiability） | 方法、数据与分析是否足够清楚 |
| 清晰度（Clarity） | 写作和呈现质量 |

五项等权，各 0–5 分，取平均。鼓励的主题包括参数高效微调、强化学习（Reinforcement Learning, RL）、代码理解、任务与基准、图推理。需要保存后点击提交，草稿不参与评审；附加的私有 Kaggle 资源可能在截止后自动公开。

来源：[论文赛道评审与提交要求](https://www.kaggle.com/competitions/gemma-4-developer-agent-paper)。

**研究建议：** 若同时参加，可围绕一个可检验问题组织实验，例如“图邻居检索能否在相同时间预算下提高跨仓库修复率”。记录成功率、耗时和失败类型，再进行移除图工具、改变时间分配等消融实验（Ablation Study）。先获得可复现结果，再决定是否投入论文写作。

## 11. 推荐参赛路线与实验记录

本节是结合已核实条件给出的工作建议，不属于官方要求。

### 11.1 首先打通一次有效评测

第一阶段目标应是：能够读取任务、启动指定模型、完成工具调用、生成补丁、验证并打包。在这条链路稳定前，不宜把主要算力投入训练。

建议先挑选少量问题描述清楚、可稳定复现的任务，覆盖不同仓库。依次检查：

1. 参考修复是否能在同一环境中通过验证。
2. 基础智能体是否能获得正确源码和测试反馈。
3. 修改是否确实进入补丁，以及补丁能否应用。
4. 超时、上下文增长和工具失败是否有明确日志。
5. 输出压缩包是否符合官方验证器要求。

### 11.2 再改进定位与修复流程

一个值得作为起点的流程是：

```text
理解问题 → 找到相关源码 → 形成可验证假设
        → 做小范围修改 → 运行相关测试
        → 根据反馈修正 → 检查差异 → 提交补丁
```

可比较普通源码搜索、向量检索、图邻居扩展及其组合。检索结果需要回到实际文件核对；图覆盖缺失、重复节点或无结果时保留回退策略。

对于时间有限的任务，优先运行能验证当前假设的相关测试。避免一次读取过多无关文件、无限重复同类搜索，或在缺少新证据时持续扩大修改范围。

### 11.3 有基线之后再评估子智能体与训练

子智能体适合明确分工的分析任务，但会增加推理和上下文成本。应比较单智能体与分工方案在相同预算下的净收益，再决定是否保留。

若准备训练 LoRA，先从失败日志判断主要瓶颈：定位、修改、工具调用格式、测试反馈理解，还是预算耗尽。针对可测量瓶颈构建材料，训练后确认适配器实际生效，并在独立验证集比较成功率与耗时。

### 11.4 推荐的实验记录字段

| 类别 | 建议记录 |
| --- | --- |
| 可复现性 | 数据版本、依赖包版本、模型路径、配置包摘要 |
| 方案设置 | 提示词版本、工具列表、生成参数、适配器版本 |
| 每题结果 | 任务标识、补丁、是否通过、失败阶段 |
| 资源成本 | 准备时间、推理时间、工具调用数、轮次、测试时间 |
| 失败类型 | 环境失败、定位失败、错误修复、未提交、预算耗尽 |
| 总体指标 | 修复率、按仓库修复率、耗时分位数、有效补丁率 |

同一轮实验尽量只改变一个关键因素。每天提交次数有限，应优先在本地或公开开发集筛选方案，再用正式提交确认表现。
